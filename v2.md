# Azigate Native Agent Gateway

**Data de referência:** 24/09/2026
**Objetivo:** adicionar ao Azigate suporte nativo a Codex, Claude Code e Google Antigravity CLI/AGY, preservando o funcionamento natural de cada agente, sem obrigá-los a operar como uma API OpenAI-compatible.

---

# 1. Resumo executivo

O Azigate atual é essencialmente um **Model Gateway**:

```text
cliente/agente
     │
     │ OpenAI Chat Completions
     ▼
   Azigate
     │
     ├── OpenAI-compatible upstream
     ├── OpenAI Responses
     └── Anthropic Messages
```

Essa arquitetura funciona quando o objetivo é:

> enviar mensagens + tools para um modelo e receber texto/tool calls.

Ela deixa deliberadamente a execução das ferramentas na máquina cliente.

O novo objetivo é diferente:

> permitir usar Codex, Claude Code e Antigravity como **agentes completos**, com seus próprios conceitos de sessão, contexto, ferramentas, permissões, subprocessos, skills, MCP, subagentes e execução de tarefas.

Portanto, o Azigate não deve tentar converter:

```text
Claude Code
Codex
AGY
```

para:

```text
POST /v1/chat/completions
```

O novo desenho deve ser:

```text
                         AZIGATE
                ┌─────────────────────┐
                │                     │
                │   Model Gateway     │
                │   existente         │
                │                     │
                │ /v1/...             │
                └──────────┬──────────┘
                           │

                ┌─────────────────────┐
                │                     │
                │ Native Agent Plane  │
                │ NOVO                │
                │                     │
                ├─────────────────────┤
                │ Codex Runtime       │
                │ Claude Runtime      │
                │ AGY Runtime         │
                └──────────┬──────────┘
                           │
                           │ ferramentas remotas
                           ▼
                    Azigate Worker
                     máquina projeto
```

A principal mudança arquitetural é esta:

```text
MODEL GATEWAY
stateless
request → model → response

+

AGENT GATEWAY
stateful
session → turns → tools → approvals → workspace
```

Essas duas responsabilidades não devem ser misturadas.

---

# 2. O que deve permanecer intacto

O funcionamento atual do Azigate deve continuar existindo.

Hoje ele possui uma superfície OpenAI-compatible para clientes como Qwen Code, Cline, Continue e outros.

Esse modo continua útil e deve permanecer:

```text
POST /v1/chat/completions
GET  /v1/models
```

O novo recurso deve ser **adicional**, não uma substituição.

Assim o Azigate passa a ter dois produtos lógicos:

| Plano       | Finalidade                                     |
| ----------- | ---------------------------------------------- |
| Model Plane | API de modelos, compatibilidade OpenAI         |
| Agent Plane | execução e controle de coding agents completos |

A separação também protege uma característica importante do Azigate atual: o gateway de modelos é essencialmente stateless.

Agentes completos, por definição, passam a introduzir:

* processos vivos;
* sessões;
* threads;
* conversation IDs;
* aprovações;
* cancelamentos;
* workers;
* workspaces;
* tarefas longas;
* processos shell;
* reconnect;
* estado persistente.

Não vale a pena contaminar a arquitetura atual com essas responsabilidades.

# 4. Regra arquitetural principal

Cada fornecedor deve ser integrado utilizando **a interface programática natural dele**.

Não implementar:

```text
Claude → OpenAI Chat Completions
AGY    → OpenAI Chat Completions
Codex  → OpenAI Chat Completions
```

para o Agent Plane.

Implementar:

```text
Codex
    → Codex app-server / Codex SDK

Claude Code
    → Claude Code SDK / stream-json

AGY
    → Antigravity CLI stream-json / Antigravity SDK
```

A normalização deve ocorrer apenas no **Control Plane do Azigate**, não apagando as capacidades particulares dos agentes.

# 5. Codex

O Codex atualmente possui a integração mais completa para este cenário.

## 5.1 Interface oficial

O `codex app-server` fornece comunicação bidirecional usando JSON-RPC e envia notificações durante a execução de um turn. Existem operações como criação, retomada e controle de threads e turns.

Além disso, existe atualmente um SDK Python oficial:

```text
openai-codex
```

que expõe conceitos nativos como:

```text
Codex
Thread
Turn
TurnHandle
models
thread_start
thread_resume
thread_fork
interrupt
steer
```

O SDK reutiliza uma autenticação Codex já existente e também pode iniciar login ChatGPT por browser ou device code.

Portanto, para o Azigate, não é mais necessário tratar Codex simplesmente como uma versão especial da Responses API.

## 5.2 Adapter Codex

Criar:

```text
src/agents/codex/
```

com aproximadamente:

```text
codex-runtime.ts
codex-session.ts
codex-events.ts
codex-approvals.ts
codex-worker.ts
codex-types.ts
```

O runtime poderá inicialmente iniciar:

```bash
codex app-server
```

e manter uma conexão JSON-RPC.

Alternativamente, um sidecar Python pode usar diretamente:

```python
openai_codex
```

O `app-server` é a opção mais interessante para o Azigate porque preserva diretamente o protocolo usado pelo próprio ecossistema Codex.

## 5.3 Sessões

Mapeamento:

```text
Azigate session
       │
       ▼
Codex thread
```

Exemplo:

```json
{
  "sessionId": "agt_123",
  "provider": "codex",
  "providerSessionId": "thread_abc",
  "workerId": "worker_b",
  "workspaceId": "backend"
}
```

Um novo turn do Azigate vira:

```text
turn/start
```

no app-server.

Cancelamento vira:

```text
turn/interrupt
```

Retomada usa:

```text
thread/resume
```

Portanto, nada precisa ser traduzido para `messages[]`.

# 6. Execução remota nativa do Codex

Codex possui uma vantagem importante: existe `codex exec-server`.

O projeto oficial descreve o `exec-server` como um servidor responsável por operações de processo e filesystem, com transporte WebSocket e RPCs para controlar subprocessos.

Isso permite a arquitetura:

```text
Máquina A

Codex app-server
      │
      │ execution environment
      ▼
────────────────────────────────────

Máquina B

codex exec-server
      │
      ├── filesystem
      ├── process
      ├── shell
      └── projeto
```

O próprio repositório Codex possui testes específicos para o split:

```text
app-server
     ↓
remote executor
     ↓
exec-server
```

Logo, para Codex, o Azigate Worker deve preferencialmente inicializar:

```bash
codex exec-server
```

em vez de reinventar filesystem e shell via MCP.

Há uma ressalva: partes da arquitetura de ambientes remotos ainda são evolutivas/experimentais. Há inclusive discussões abertas no repositório pedindo um contrato mais estável para remote workers em escala.

Consequentemente:

```text
CODEX_REMOTE_EXECUTION=experimental
```

deve inicialmente ficar atrás de feature flag.

Também é recomendável pinning da versão Codex.

# 7. Claude Code

Claude Code não possui atualmente um equivalente direto e documentado ao `codex app-server`.

Por outro lado, possui uma excelente interface programática.

Claude Code suporta:

```bash
claude -p
```

e formatos:

```text
text
json
stream-json
```

Também suporta entrada `stream-json`, retomada de sessão, seleção de tools e MCP.

Exemplo conceitual:

```bash
claude -p \
  --input-format stream-json \
  --output-format stream-json
```

Assim o Azigate pode conversar com Claude Code como um processo persistente, sem converter eventos Claude para OpenAI.

# 8. Claude Code e autenticação

Isso resolve outro problema existente no Azigate.

Hoje o projeto reproduz diretamente partes do OAuth/HTTP do Claude.

No Agent Plane isso não deve ser feito.

Claude Code suporta login usando uma assinatura Claude Pro ou Max oficialmente.

Portanto:

```text
máquina A

claude
  ↓
login oficial
  ↓
credencial armazenada pelo próprio Claude Code
```

Depois o Azigate apenas inicia:

```bash
claude -p ...
```

e deixa o próprio Claude Code lidar com:

```text
autenticação
refresh
modelo
limites
session
protocolos internos
```

Isso reduz fortemente acoplamento com APIs privadas.

Para o Agent Plane, a regra deve ser:

> **Nunca copiar, reinterpretar ou renovar manualmente credenciais Claude se o Claude Code oficial puder fazê-lo.**

```bash
claude -p \
```


Não converter isso imediatamente para:

```json
{
  "choices": [...]
}
```

Guardar e transmitir esses eventos como Claude.

```bash
--resume <session-id>
```

```bash
--continue
```

Portanto:

```text
Azigate session ID
      ↓
Claude session_id
```

deve ser persistido.

Exemplo:

```json
{
  "id": "agt_aF42",
  "provider": "claude",
  "nativeSessionId": "01J...",

  "workspace": "my-api"

```

Se o processo morrer:

```text
novo processo
     +
--resume nativeSessionId
```

# 11. Claude executando o projeto na máquina B

Existe uma dificuldade importante.

Se:

```text
Claude Code = máquina A
projeto     = máquina B
```

então as tools nativas:

```text
Read
Write
Edit
Bash
```

da máquina A não devem acessar o projeto.

A solução natural oferecida pelo Claude Code é MCP.

Claude Code permite carregar MCP servers usando:

```bash
--mcp-config
```

e controlar quais ferramentas MCP podem ser usadas usando:

```bash
--allowedTools
```

Também existe:

```bash
--permission-prompt-tool
```

para encaminhar pedidos de aprovação para uma ferramenta MCP.

Assim:

```text
Claude Code A
     │
     │ MCP
     ▼
Azigate Worker B
     │
     └── projeto
```

O Claude continua sendo Claude Code completo.

Não estamos transformando Claude em OpenAI.

Estamos apenas utilizando um mecanismo oficial de extensão do Claude Code para colocar as ferramentas no computador correto.

# 12. Segurança Claude

Uma sessão remota deve iniciar com as tools locais perigosas da máquina A desabilitadas.

Por exemplo:

```text
Read     local A → DENY
Write    local A → DENY
Edit     local A → DENY
Bash     local A → DENY
```

e:

```text
mcp__azigate_workspace__read
mcp__azigate_workspace__write
mcp__azigate_workspace__edit
mcp__azigate_workspace__exec
```

habilitadas.

Resultado:

```text
Claude reasoning
      │
      ▼
tool request
      │
      ▼
MCP
      │
      ▼
Máquina B
```

O Azigate jamais deve permitir que um `workspaceId` fornecido por um cliente vire diretamente um path arbitrário.

Errado:

```json
{
  "cwd": "/etc"
}
```

Correto:

```json
{
  "workspace": "backend"
}
```

e no worker:

```text
backend → /home/isaias/projetos/backend
```

# 13. Google Antigravity / AGY

O AGY também já fornece uma superfície própria de automação.

Seu modo headless oficial é:

```bash
agy -p
```

e suporta:

```text
text
json
stream-json
```

O `stream-json` é NDJSON tipado e contém eventos como:

```text
init
step_update
result
```

Os eventos incluem inclusive informações de tool calls e subagentes.

Portanto, novamente:

> não há razão para converter AGY para OpenAI Chat Completions.

# 16. Autenticação AGY

O modo headless do AGY reutiliza as credenciais já armazenadas pela CLI.

A própria documentação especifica que uma execução headless usa cached credentials e que a autenticação deve ser feita anteriormente em uma sessão interativa.

Portanto:

```text
agy
 ↓
Google login oficial
 ↓
credencial oficial
 ↓
Azigate apenas inicia o processo
```

Não criar OAuth próprio para AGY.

Ele oferece uma API Python programática baseada no mesmo harness de agentes e suporta:

```text

structured output
persistence

multimodal
```

Ele é interessante como backend futuro.


Portanto:


# 18. Não usar AGY Remote Control como API

AGY também possui Remote Control e daemon:

```bash
agy remote-control start
```

Mas esse recurso foi desenvolvido principalmente para controlar instâncias através da interface Antigravity/browser.

Ele não deve ser a base do protocolo Azigate.

Usar:

```text
Headless stream-json
```

ou:

```text
Antigravity SDK
```

é arquiteturalmente mais apropriado.

# 19. Azigate Worker

A parte mais importante para executar projetos remotos será um novo componente:

```text
azigate-worker
```

Ele roda na máquina onde existe o projeto.

Exemplo:

```bash
azigate-worker \
  --gateway https://ia.example.com \
  --worker dev-machine \
  --token ...
```

Configuração:

```yaml
workspaces:
  backend:
    path: /home/user/projects/backend

  frontend:
    path: /home/user/projects/frontend
```

O servidor nunca aceita um path arbitrário vindo do cliente.

Apenas:

```text
workspaceId
```

# 21. Transporte Worker ↔ Gateway

Evitar exigir que a máquina B abra uma porta pública.

Preferir:

```text
Worker B
   │
   │ outbound TLS WebSocket
   ▼
Azigate A
```

Assim:

```text
B inicia conexão
A não precisa entrar diretamente em B
```

Isso funciona melhor atrás de:

```text
NAT
firewall
rede doméstica
VPN
CGNAT
```

Protocolo conceitual:

```json
{
  "type": "worker.register",
  "workerId": "devbox",
  "capabilities": [
    "mcp",
    "shell",
    "filesystem",
    "codex-exec"
  ]
}
```

O gateway associa:

```text
worker
workspace
session
provider
```

# 22. API pública do Agent Plane

Mesmo usando protocolos nativos internamente, vale ter uma API comum do Azigate para lifecycle.

Por exemplo:

```text
POST /agent/v1/sessions
POST /agent/v1/sessions/:id/turns
GET  /agent/v1/sessions/:id
GET  /agent/v1/sessions/:id/events
POST /agent/v1/sessions/:id/cancel
POST /agent/v1/approvals/:id
DELETE /agent/v1/sessions/:id
```

Essa API **não é OpenAI-compatible**.

Ela representa conceitos de agente.

Criar sessão:

```json
{
  "provider": "claude",
  "worker": "devbox",
  "workspace": "backend",
  "model": "sonnet",
  "permissionMode": "review"
}
```

Resposta:

```json
{
  "id": "agt_0193...",
  "provider": "claude",
  "status": "ready",
  "nativeSessionId": null
}
```

Enviar tarefa:

```json
{
  "input": "Analise o endpoint /users e implemente paginação."
}
```

# 23. Eventos comuns do Azigate

Apesar de cada provider manter seus eventos nativos, o Azigate pode oferecer uma camada mínima de eventos universais:

```text
session.started
turn.started
message.delta
reasoning.delta
tool.started
tool.completed
approval.required
subagent.started
subagent.completed
usage
turn.completed
turn.failed
session.closed
```

Mas sempre incluir:

```json
{
  "native": { ... }
}
```

contendo o evento original.

Exemplo:

```json
{
  "event": "tool.started",
  "sessionId": "agt_123",
  "provider": "agy",
  "tool": "run_command",

  "native": {
    "...": "evento original do AGY"
  }
}
```

Assim o Azigate consegue oferecer uma API universal sem destruir características específicas do fornecedor.

# 27. Separação de processos

Recomendação:

```text

```

responsável pelo funcionamento atual.

```text

azigate-agentd
```

responsável por:

```text
Claude
```

Motivos:

* isolamento;
* crashes de CLI não derrubam o gateway;
* lifecycle diferente;
* limites diferentes;
* deploy independente;
* segurança;
* observabilidade;
* futura escala horizontal.

# 28. Persistência

O Model Gateway atual pode continuar sem banco.

O Agent Plane deve guardar no mínimo:

```text
session_id
provider
native_session_id
worker_id
workspace_id
status
created_at
updated_at
model
permission_mode
```

Para primeira versão:

```text
SQLite
```

é suficiente.

Posteriormente:

```text
PostgreSQL
```

se houver múltiplas instâncias.

Não persistir:

```text
OAuth access token
refresh token
API key
prompt completo
tool arguments
código
```

na mesma tabela.

Credenciais continuam sob responsabilidade das CLIs ou de um secret store.

# 29. Aprovações

A aprovação deve ser uma entidade de primeira classe.

Exemplo:

```json
{
  "approvalId": "apr_123",
  "sessionId": "agt_456",
  "provider": "claude",
  "tool": "shell_exec",
  "summary": "npm install package-x",
  "status": "pending"
}
```

API:

```text
POST /agent/v1/approvals/apr_123
```

```json
{
  "decision": "allow"
}
```

ou:

```json
{
  "decision": "deny"
}
```

Claude Code suporta um MCP `permission-prompt-tool`, permitindo que o Azigate implemente esse fluxo sem contornar o sistema de permissões do Claude.

AGY possui regras explícitas de permissão no modo headless e recomenda concessões específicas em vez de `--dangerously-skip-permissions`.

Logo:

> `dangerously-skip-permissions` nunca deve ser o comportamento padrão do Azigate.

# 30. Segurança do Workspace

Cada worker deve possuir uma jail lógica.

Exemplo:

```text
workspace backend
root = /home/user/projects/backend
```

Operações como:

```text
../../etc/passwd
/home/outro-projeto
/etc
~/.ssh
```

devem ser rejeitadas.

Sempre fazer:

```text
realpath
↓
verificação do prefixo permitido
↓
operação
```

Symlinks também precisam ser resolvidos antes da autorização.

---

# 31. Shell

Não permitir:

```text
shell.exec(command: string)
```

sem controle.

Preferir:

```json
{
  "argv": ["npm", "test"],
  "cwd": "."
}
```

em vez de:

```json
{
  "command": "npm test && rm -rf ..."
}
```

Quando shell completo for necessário, passar pelo sistema de aprovação.

---

# 32. Autenticação entre B e A

Worker deve possuir sua própria identidade.

Exemplo:

```text
worker token
+
TLS
```

Melhor ainda:

```text
mTLS
```

posteriormente.

Cada worker deve ter scopes:

```text
worker:connect
workspace:backend
workspace:frontend
```

Nunca reutilizar:

```text
GATEWAY_API_KEY
```

do `/v1/chat/completions`.

Agent Plane e Model Plane devem ter credenciais separadas.



ou em produção:

# 47. Decisão recomendada

A implementação deve seguir quatro princípios:

1. **Manter `/v1` atual intacto.**
2. **Criar um Agent Plane separado e stateful.**
3. **Usar o protocolo/runtime oficial de cada agente.**
4. **Executar projetos remotos através de workers, usando `exec-server` para Codex e MCP para Claude/AGY.**

A ordem recomendada de implementação é:

```text
Agent Core
   ↓
AGY headless
   ↓
Claude Code headless
   ↓
Codex app-server
   ↓
Azigate Worker
   ↓
Claude + Worker
   ↓
AGY + Worker
   ↓
Codex exec-server
```

AGY e Claude são mais simples para validar o novo lifecycle.

Codex deve entrar depois no modo completo porque o app-server é mais rico, e a parte de remote execution via exec-server ainda possui áreas experimentais apesar de já existir oficialmente no código e nos testes do projeto.

A consequência mais importante é que **o Azigate não precisa mais reproduzir as APIs privadas dos CLIs para oferecer agentes completos**. O Agent Plane pode delegar autenticação, sessão, contexto e comportamento agentic às ferramentas oficiais, ficando responsável por aquilo que realmente pertence ao gateway:

```text
routing
security
session mapping
workers
workspace isolation
approvals
observability
remote transport
```

Esse é o limite arquitetural adequado para a evolução do projeto.
